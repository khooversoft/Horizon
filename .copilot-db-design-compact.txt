Executive summary
This design provides a deliberately small relational core for two commerce models: ordinary high-volume storefront orders and account-only recurring subscriptions. Both models converge on the same order, payment, fulfillment, and audit structures. A subscription is a schedule and reusable order template; each successful renewal creates an ordinary sales order.
Key correction  Inventory is outside the scope because contracted fulfillment companies supply and ship the products. Therefore subscription renewal does not reserve inventory. It validates that the SKU and fulfillment route remain active, creates an order, initiates payment, and advances the next processing date only after the configured success point.

All base tables and private implementation objects reside in AppDbo. Runtime consumers receive SELECT and EXECUTE permissions only on the App schema. App views expose read contracts; App stored procedures expose write and command contracts. API code never receives direct table permissions.
The database supports multiple storefronts through Site and SiteProduct records. A single customer account can purchase across sites, while catalog visibility, branding, default currency, fulfillment routing, and customer-facing order numbers remain site-aware.
1. Goals, scope, and guiding decisions
1.1 Goals
Provide the minimum relational model needed to launch product sales and subscriptions without creating a short-lived prototype.
Support headless APIs consumed by multiple storefronts and one administration site.
Keep the catalog generic enough for apparel, pet food, physical merchandise, and recurring services.
Make every financial and renewal operation retry-safe and auditable.
Use explicit stored procedures as the domain command interface and views as stable read contracts.
Generate clean DACPAC artifacts from an SQL project and support automated deployment.
Provide sufficient object definitions, invariants, workflows, and naming rules for AI-assisted implementation.
1.2 Explicit non-goals for the initial release
Warehouse inventory, stock reservations, receiving, purchasing, and cost accounting.
General-purpose promotion-rule engine; only simple order or subscription discounts are modeled.
Marketplace sellers, split settlements, commissions, or vendor payouts.
Full ERP, CRM, tax engine, email campaign platform, or content-management system.
Storing sensitive payment card data, card verification values, or payment processor secrets.
Hard deletion of completed orders, payment history, or subscription events.
1.3 Core decisions
Decision | Design consequence
One order system | Guest purchases, account purchases, and subscription renewals all create AppDbo.SalesOrder and AppDbo.SalesOrderItem rows.
Product and variant separation | Product is customer-facing content; ProductVariant is the purchasable SKU with price, weight, sale state, and fulfillment code.
No inventory | Availability means sellable and fulfillable, not quantity on hand.
Historical snapshots | Order items and order addresses retain the values used at purchase time.
Email-centered customer key | Normalized email is the business CustomerId, with Entra issuer and subject retained as immutable identity linkage.
Schema security boundary | AppDbo is private. App is the only runtime-accessible schema.
Append-oriented finance | PaymentTransaction records every authorization, capture, failure, void, refund, and dispute.
Idempotent integrations | Provider event IDs and business idempotency keys are protected by unique constraints.
Minimal extensibility | Every table includes optional JsonData for uncommon metadata, but core searchable and constrained data remains relational.

2. Architecture and trust boundaries
2.1 Logical architecture
Storefront A / Storefront B / Admin UI              |        Headless API services              |    C# database client assembly              |       App views + procedures              |      AppDbo tables + internals       /                    \Azure Data Lake media    Payment / fulfillment providers

The C# database client library is the only code layer that understands SQL parameter names, result-set shapes, and stored-procedure names. API services depend on typed command and result contracts rather than referencing ADO.NET details throughout the application.
2.2 Transaction ownership
Each business-changing App stored procedure owns its SQL transaction.
The API must not open a long transaction spanning network calls to payment or fulfillment providers.
Provider calls use an outbox/background-worker sequence or an explicit two-step state machine.
Webhook ingestion records the original message before processing and deduplicates by provider plus external event ID.
Every procedure that changes money, order state, or subscription timing writes an audit event in the same database transaction.
2.3 Multi-site model
A Site represents a customer-facing website or sales channel. It does not create a separate database or duplicate customer table. Site-aware catalog and order records isolate presentation and business defaults while preserving a shared operational core.
Object | Site behavior
Site | Defines SiteId, name, host, default currency, fulfillment provider, status, and optional settings.
SiteProduct | Controls whether a shared product is visible on a site and permits site-specific display sequence or title override.
Cart | Belongs to exactly one site.
SalesOrder | Belongs to exactly one site and snapshots site-facing information as needed.
Subscription | Belongs to one site because renewal pricing, currency, and fulfillment routing are site-specific.
Customer | Shared across sites by normalized email.
Employee role | Scoped globally or to a SiteId, depending on EmployeeRole.SiteId.

3.2 Required common columns
Every table uses an internal identity key and a domain-friendly external key. Most external IDs are short, stable, human-readable values. The exceptions are email-based CustomerId and provider identifiers, which require longer columns.
Column | Type | Rule
RowId | bigint IDENTITY(1,1) | Internal primary key. Never exposed as the public API identifier.
<Entity>Id | nvarchar(50) | Required business identifier for most entities; unique within its stated scope.
JsonData | varchar(max) NULL | Optional valid JSON for uncommon metadata. Add CHECK (JsonData IS NULL OR ISJSON(JsonData)=1).
CreatedUtc | datetime2(3) | Required where the row has a lifecycle.
ModifiedUtc | datetime2(3) | Required on mutable entities.
RowVersion | rowversion | Required on mutable command targets for optimistic concurrency.

Email key exception  CustomerId is the normalized email address and must be nvarchar(320), not nvarchar(50). Truncating an email to 50 characters would create avoidable account collisions and sign-in failures. The design preserves the requested email-centered account model while also storing Entra issuer and subject so identity linkage survives provider changes and can be investigated safely.

3.3 Identifier rules
IDs are lowercase ASCII slugs where human readability is useful: custom-tee-001, dog-food-adult-chicken-12lb, badpet-main.
Provider-controlled identifiers use provider lengths rather than nvarchar(50), usually nvarchar(200) or nvarchar(255).
CustomerId is normalized by the API using trim plus invariant lowercase before calling SQL. SQL repeats the normalized-value check.
Email changes require a dedicated account procedure; they are never implemented as an ad hoc update.
RowId is used for foreign keys inside the database for compact joins. Public procedures accept business IDs and resolve them to RowId under transaction.
3.4 Money, time, and JSON
Money uses decimal(19,4), never SQL money.
Currency uses char(3) ISO-style codes and references Currency.
All database timestamps are UTC datetime2(3).
JsonData is never the sole location for price, quantity, status, email, SKU, next processing date, or provider transaction IDs.
JSON fields are validated with ISJSON. Frequently queried JSON properties must be promoted to relational columns.
4. Security and identity design
4.1 Entra External ID
Microsoft Entra External ID authenticates customers and can map OIDC claims including subject and email. The database treats normalized email as CustomerId per the requested business rule, while CustomerIdentity stores Issuer and Subject as the durable authentication linkage. This prevents the application from relying only on a mutable profile attribute.
4.2 Customer authorization
Customers do not have application roles. A customer can act only on resources linked to the authenticated CustomerId or to a validated guest cart token. Stored procedures do not accept an arbitrary customer email as authorization proof; the API derives the actor from the validated access token and sets trusted SQL session context.
4.3 Employee authorization
Employees are assigned only one or more of the following roles: owner, contributor, or read-only. Customer accounts are never inserted into employee-role tables.
Role | Intended capability
owner | Full administration, employee access management, catalog publishing, order corrections, subscription administration, and refund initiation.
contributor | Catalog management, customer service, order and subscription operations; no employee-role administration.
read-only | Administrative read views only; no state-changing procedures.

4.4 Database roles and grants
CREATE ROLE [app_api_runtime];CREATE ROLE [app_deployer];GRANT SELECT, EXECUTE ON SCHEMA::[App] TO [app_api_runtime];DENY SELECT, INSERT, UPDATE, DELETE ON SCHEMA::[AppDbo] TO [app_api_runtime];

In production, role grants should be narrowed further if separate API identities exist for storefront, admin, payment worker, and subscription worker. The schema rule is the minimum security boundary, not a reason to give every runtime service every procedure.
4.5 Session context
EXEC sys.sp_set_session_context @key=N'ActorType', @value=N'Customer', @read_only=1;EXEC sys.sp_set_session_context @key=N'ActorId', @value=@CustomerId, @read_only=1;EXEC sys.sp_set_session_context @key=N'CorrelationId', @value=@CorrelationId, @read_only=1;

Audit-writing procedures read ActorType, ActorId, CorrelationId, ApplicationName, and RequestId from trusted session context. The API must not copy unvalidated browser claims directly into this context.

7. Constraints and invariants
Customer.CustomerId equals the canonical normalized email and is unique.
CustomerIdentity has a unique Issuer + Subject pair and belongs to one customer.
A subscription requires CustomerRowId, active CustomerAddress, active PaymentMethod, at least one active SubscriptionItem, and complete customer contact data.
A guest cart has GuestTokenHash and no CustomerRowId. An account cart has CustomerRowId; GuestTokenHash may remain temporarily during merge only.
Only one active cart per SiteRowId + CustomerRowId is allowed through a filtered unique index.
Only one CartItem per CartRowId + ProductVariantRowId is allowed.
Closed, converted, expired, or merged carts cannot be modified.
SalesOrder totals are nonnegative and GrandTotal equals subtotal minus discounts plus shipping plus tax within the procedure calculation.
SalesOrderItem is immutable after order placement except through explicit administrative correction procedures that append an audit event.
PaymentTransaction and SubscriptionEvent are append-only by permission and procedure design.
ProviderCode + ExternalMessageId is unique in InboxMessage.
ProviderCode + ProviderEventId is unique in PaymentTransaction where ProviderEventId is not null.
Subscription renewal uniqueness is enforced using SubscriptionRowId + scheduled processing occurrence or a RenewalKey.
JsonData and other JSON payload columns pass ISJSON checks whenever non-null.
No procedure accepts RowId from a public API. Business IDs are resolved internally.

8.1 Procedure contract standard
First parameters: @CorrelationId uniqueidentifier and @IdempotencyKey nvarchar(100) where retry safety is required.
Identifiers are business IDs, not RowId.
Use SET NOCOUNT ON and SET XACT_ABORT ON.
Validate authorization context before reading or changing private rows.
Own the transaction for multi-table changes.
Use explicit column lists for every INSERT and SELECT.
Return one summary result set plus named logical child result sets documented in the C# client.
Return application error code and safe message; log internal diagnostic details separately.
Never return provider secrets or raw sensitive payloads to storefront clients.
Write BusinessEvent and domain history in the same transaction as the state change.

10. Critical workflows
10.1 Guest purchase
Create guest cart and return raw token to browser once; SQL stores only hash.
Add active variants; estimate price.
At checkout, collect email and immutable shipping/billing address fields.
Order_CreateFromCart resolves current price, creates order snapshots, converts cart, inserts audit/outbox.
Background worker creates the provider payment operation using an idempotency key.
Webhook is stored in inbox, processed once, appends PaymentTransaction, and updates payment/order summary.
Paid order is submitted to contracted fulfillment provider; provider statuses update Fulfillment.
10.2 Account purchase
Resolve account from validated Entra identity.
Get or create site-specific active cart.
Optionally merge a guest cart.
Use saved or one-time address at checkout.
Create the same ordinary SalesOrder used for guest purchase.
Expose order history by CustomerRowId and validated session context.
10.3 Subscription creation
Require authenticated customer account.
Require FirstName/LastName or recipient name, phone, valid shipping address, and active reusable provider payment method.
Require at least one subscription-eligible active variant.
Create subscription as draft, then activate after validation.
Calculate NextProcessUtc and append SubscriptionActivated event.
10.4 Subscription renewal
Scheduler calls Subscription_ClaimDueBatch using short leases so multiple workers cannot process the same subscription concurrently.
Create a deterministic RenewalKey from SubscriptionId and scheduled occurrence.
Revalidate subscription, customer, address, payment method, site, product, variant, and fulfillment route.
Reprice current recurring items and apply the current simple subscription discount.
Create one ordinary SalesOrder and SalesOrderItems as immutable snapshots.
Create Payment plus payment-request outbox message. No inventory reservation occurs.
At the configured success point, usually successful authorization or capture, mark renewal successful and advance NextProcessUtc.
On failure, retain the order/payment attempt, increase FailureCount, schedule retry, and append SubscriptionRenewalFailed.
Success-point rule  The implementation must choose one renewal success point and apply it consistently. Capture is the simplest default for physical goods. If authorization is used, the order may proceed before capture only when the payment and fulfillment policy explicitly allows it.

10.5 Webhook idempotency
Verify provider signature in the API before database processing.
Call Integration_InboxAccept with ProviderCode and ExternalMessageId.
Rely on the unique constraint to decide whether this is new or duplicate.
Process the claimed inbox row inside a bounded transaction.
Append PaymentTransaction or Fulfillment update with provider identifiers protected by unique constraints.
Mark inbox processed; duplicates return success without repeating side effects.
10.6 Cart merge
Lock guest and account carts in deterministic order.
For matching variants, add quantities while respecting maximum policy.
Move unique lines.
Mark guest cart merged and point it to the surviving cart in JsonData or a dedicated MergedIntoCartRowId extension.
Return the account cart read model.
Make repeated merge requests return the same surviving cart.
11. Auditing and historical integrity
Use temporal history for mutable high-value summaries such as SalesOrder, Payment, Subscription, CustomerAddress, and Fulfillment where point-in-time reconstruction is valuable.
Use domain-specific append-only histories for order statuses, payment transactions, and subscription events.
Use BusinessEvent for actor, reason, source, correlation, and affected aggregate.
Use InboxMessage and OutboxMessage for integration evidence and retry history.
Deny runtime UPDATE and DELETE on append-oriented tables. Only App procedures insert rows.
Do not place full card numbers, security codes, access tokens, secrets, or unnecessary personal information in audit JSON.
Consider SQL Ledger later only if cryptographic tamper evidence is a contractual or regulatory requirement.

12. Media and Azure Data Lake
Binary images and video are not stored in SQL. ProductMedia stores references and metadata only. Storage paths should be stable, not signed URLs. The API creates time-limited access URLs or serves media through an approved CDN.
/sites/{siteId}/products/{productId}/{variantId?}/{mediaId}/{fileName}

MediaTypeCode distinguishes image, video, thumbnail, size-chart, and document.
StorageUri is the canonical internal URI. PublicUrl should not be persisted when it is time-limited.
AltText is required for customer-visible images.
ProductVariantRowId is nullable so media can apply to the entire product or one variant.
IsPrimary plus DisplaySequence controls presentation; a filtered unique index may enforce one primary media item per product/variant/media type.
Deletion is archive-first. A background process may remove unreferenced blobs only after retention checks.

16. Testing and acceptance criteria
16.1 Database build tests
dotnet build produces a DACPAC with no unresolved references.
All AppDbo tables have RowId, business ID, and JsonData.
Every JsonData column has an ISJSON check.
No App view or procedure accidentally exposes payment tokens or raw provider secrets.
Runtime roles have no direct DML permissions on AppDbo.
16.2 Domain integration tests
Guest cart can be created, modified, converted, and expired.
Authenticated cart can merge a guest cart repeatedly without duplicate lines.
Order creation called twice with the same idempotency key returns the same order.
Catalog price changes after purchase do not change SalesOrderItem snapshots.
Subscription cannot activate without account, contact, address, payment method, and items.
Two renewal workers cannot create two orders for one scheduled occurrence.
Duplicate payment webhook does not create duplicate PaymentTransaction or capture totals.
Failed renewal does not advance NextProcessUtc as though successful.
Successful renewal creates a normal SalesOrder linked to SourceSubscriptionRowId.
Customer cannot read another customer’s cart, order, address, payment summary, or subscription.
Read-only employee cannot execute mutation procedures.
Contributor cannot grant owner access.
Retired variant remains visible in historical order data but cannot be newly purchased.

Appendix B. Reference notes
The supplied MPV tables workbook was used as the baseline object list and expanded only where required for multi-site support, contracted fulfillment, employee roles, and implementation completeness.
Microsoft Entra External ID OIDC claims mapping distinguishes the subject identifier from the email claim. This design therefore retains Issuer and Subject even though normalized email is the requested CustomerId.
Stripe supports idempotency keys for safely retrying create/update operations, and its webhook guidance recommends guarding against processing an event twice. This design uses both request idempotency keys and unique provider event constraints.
SQL projects aggregate SQL files and generate a DACPAC through dotnet build. This design uses that project format and a CI/CD deployment path.
